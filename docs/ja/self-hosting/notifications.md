# 通知

Ecoku は、新しいコメントがあったときにブロガーへ通知し、訪問者のコメントに返信が付いたときにその訪問者へメールで知らせることができます。通知は管理画面の「通知設定」（通知设置）ページで設定し、インスタンス内のすべてのサイトに適用されます。

| チャネル | 送信先 |
| --- | --- |
| メール（SMTP） | ブロガー：入力した宛先リストに送ります。訪問者：返信されたコメントに残されたメールアドレスに送ります。 |
| Telegram ボット | ブロガーにのみ送ります。入力したユーザー、グループ、チャンネルの ID に送ります。 |

## 有効にする前の準備

- `app/config.yaml` に `notifications.instance_public_url` が設定されていること。設定されていないと、どのチャネルも有効にできません。
- `ecoku.env` に `ECOKU_NOTIFICATION_ENCRYPTION_KEY` が設定されていること。SMTP パスワードと Bot Token は、このキーで暗号化しないと保存できません。
- サーバーが外部の SMTP ポート（一般的には 465 または 587）または `api.telegram.org` にアクセスできること。クラウド事業者によっては、SMTP の送信ポートがデフォルトでブロックされています。

## 通知が送られるタイミング

「ブロガー」かどうかは、コメントの保存時に記録されたブロガーの印、つまりそのコメントが[ブロガーの合言葉](./admin#blogger)で投稿されたかどうかで判断します。

| 場面 | ブロガーへの通知（メール / Telegram） | 返信された訪問者へのメール |
| --- | :---: | :---: |
| 訪問者がルートコメントを投稿 | 送信 | — |
| 訪問者が訪問者に返信 | 送信 | 送信 |
| 訪問者がブロガーに返信 | 送信 | — |
| ブロガーがルートコメントを投稿 | 送信しない | — |
| ブロガーが訪問者に返信 | 送信しない | 送信 |
| ブロガーがブロガーに返信 | 送信しない | — |

補足：

- 返信された訪問者がメールアドレスを残していない場合や、返信した人と返信された人のメールアドレスが同じ場合（自分への返信）は、訪問者へのメールは送りません。
- 通知が送られる前に返信先のコメントが削除された場合、訪問者へのメールは取り消されます。
- 通知が送られる前にコメント自体が削除された場合、ブロガー向けのメールと Telegram メッセージも取り消されます。すでに送られた通知については[コメントを削除した後](#after-deletion)を参照してください。
- 訪問者への返信通知は、メールチャネルが有効なときにだけ送られます。個別のスイッチはありません。メールチャネルを無効にすると、訪問者への返信通知も送られなくなります。
- Telegram で訪問者に通知することはありません。

## メール

| 項目 | 説明 |
| --- | --- |
| SMTP サーバー | 例：`smtp.example.com`。 |
| ポート | メール事業者の指定に従って入力します。一般的には 465（SSL/TLS）または 587（STARTTLS）です。 |
| 暗号化方式 | `SSL/TLS`：接続時から暗号化します。`STARTTLS`：通常の接続を確立してから暗号化に切り替えます。暗号化しない SMTP には対応していません。 |
| ユーザー名 | 空でもかまいません。空の場合は SMTP 認証を行いません。パスワードは引き続き必須なので、認証が不要なサーバーでは任意の値を入力してください。 |
| パスワード | 保存後は「設定済み」（已设置）とだけ表示されます。空のままにすると変更しません。 |
| 送信元アドレス | メールの From アドレスです。多くの事業者は、ログインアカウントと一致することを求めます。 |
| 通知の宛先 | ブロガー向け通知を受け取るメールアドレスです。複数入力でき、Enter キーまたはカンマで区切ります。 |

「テストメールを送信」（发送测试邮件）は、フォームに入力中の値（パスワードが空の場合は保存済みのパスワード）を使って宛先にテストメールを送ります。事前に保存する必要はありません。失敗した場合は、接続タイムアウト、認証の失敗、TLS ハンドシェイクの失敗など、原因がページに表示されます。

メールにはプレーンテキスト版と HTML 版の両方が含まれます。HTML 版はコメント欄や管理画面と同じ紙と墨の配色を使い、文字は受信端末に搭載されている中国語・欧文のサンセリフフォントで表示されます。Web フォントは読み込みません。ダークモードに対応したメールクライアントでは自動的にダーク配色になります。内容は種類によって異なります。

- ブロガーが新しいコメントを受け取った場合：記事タイトル、投稿日時、コメントした人とコメント本文、「查看原文」（元の記事を見る）リンク。
- ブロガーが新しい返信を受け取った場合：記事タイトル、投稿日時、返信されたコメント、返信した人と返信の本文、「查看原文」（元の記事を見る）リンク。
- 訪問者が返信を受け取った場合：記事タイトル、返信日時、訪問者自身のコメント、返信の本文、「查看回复」（返信を見る）リンク。

日時はコメント欄と同じくコンテナの `TZ` で表示し、`2026/09/29 10:18 (UTC+8)` のように UTC との時差を併記します。ブロガー本人のコメントには、ニックネームの後にサイトで設定したバッジが表示されます。

スタンプは、サイトでスタンプパックが有効で、画像が現在のスタンプ一覧と同じオリジンにある場合にだけ画像として表示されます。画像はコメント欄と同じく、スタンプを置いているサーバーから読み込まれます。メールクライアントが外部画像をブロックしている場合は `[表情：标签]`（[スタンプ：ラベル]）と表示されます。それ以外の場合とプレーンテキスト版では、常に `[表情：标签]` と表示されます。

件名の形式：

- ブロガー向け通知：「您在 [站点名称] 上有新评论：[文章标题]」（[サイト名] に新しいコメントがあります：[記事タイトル]）または「您在 [站点名称] 上有新回复：[文章标题]」（[サイト名] に新しい返信があります：[記事タイトル]）
- 訪問者向け返信通知：「你在 [站点名称] 的评论收到了回复：[文章标题]」（[サイト名] でのあなたのコメントに返信がありました：[記事タイトル]）

記事タイトルが 60 文字を超える場合は切り詰めます。ページにタイトルがない場合、件名にタイトルは付きません。差出人の表示名はサイト名で、アドレスは「送信元アドレス」の値のままです。メールには `Auto-Submitted: auto-generated` ヘッダーが付くため、自動応答プログラムは通常返信しません。

## Telegram

1. Telegram で [@BotFather](https://t.me/BotFather) からボットを作成し、Bot Token を取得します。
2. ボットがメッセージを送れるようにします。個人チャットの場合は、先にボットにメッセージを 1 通送ります。グループやチャンネルの場合はボットを追加し、チャンネルではさらに管理者にする必要があります。
3. 送信先の ID を調べます。個人ユーザーは `123456789` のような数字の列で、グループとチャンネルは通常 `-100` で始まります（例：`-1001234567890`）。
4. 管理画面に Bot Token と送信先 ID（複数可）を入力し、「テストメッセージを送信」（发送测试消息）で確認してから保存します。

メッセージには、サイト名、記事タイトル、投稿日時、コメントした人または返信した人、返信された元のコメント（引用として表示、最大 400 文字）、本文（最大 1000 文字）が含まれ、末尾に「元の記事を見る」（查看原文）リンクが付きます。スタンプは `[表情：标签]`（[スタンプ：ラベル]）と表示されます。

## 配信の仕組み

通知はコメントの投稿時に同期的には送られません。コメントと、それに伴って送る通知は、同じデータベーストランザクションで送信待ちキューに書き込まれ、バックグラウンドタスクが 3 秒ごとにまとめて取り出して送信します。そのため、次のようになります。

- メールサーバーに一時的に接続できなくても、訪問者のコメント投稿には影響しません。
- 宛先ごとに別々のレコードになり、個別に再試行されます。1 つのアドレスで失敗しても、ほかのアドレスには影響しません。
- 失敗すると 2、4、8、16、32、64、128 分の間隔で再試行し、合計 8 回試してもだめなら諦めます。
- 再試行しても成功しない失敗は、その場で諦めます：宛先のメールボックスが存在しない、またはサーバーがメールを拒否した場合（SMTP 55x）や、Telegram がチャットを見つけられない、またはボットが外された・ブロックされた場合（HTTP 400/403）です。Telegram から速度制限を求められた場合（HTTP 429）は、指定された待ち時間だけ遅らせます。
- 送信済み、取り消し、諦めたレコードは 30 日間保持され、その後自動的に削除されます。
- 通知の送信先はキューに入った時点で確定します。その後チャネルを無効にしたり宛先を変更したりしても、すでにキューに入った通知はそのまま配信されます。
- 「送信済みだが結果をまだ記録していない」瞬間にプロセスがクラッシュすると、再起動後にもう一度送られることがあります。まれに通知が重複して届く場合があります。

ログには通知の番号、エラーの種類、回数だけを記録し、宛先アドレス、コメント内容、認証情報は記録しません。

## コメントを削除した後 {#after-deletion}

管理画面でコメントを削除すると、次のようになります。

- まだ送られていない通知は送られません。ブロガー向けのメールと Telegram メッセージも含みます。
- このコメントへの返信があっても、その作成者にはメールが送られなくなり、キューに記録されていたそのメールアドレスも削除されます。
- すでに送られた Telegram メッセージは「这条评论已被删除，通知内容已移除。」（このコメントは削除され、通知の内容は取り除かれました）に書き換えられ、サイト名と記事タイトルだけが残ります。
- すでに送られたメールは取り消せません。

次の場合は、送信済みの Telegram メッセージを書き換えられません：通知の送信から 30 日を超えてレコードが削除されている場合、書き換えが終わる前にその墓標を完全に削除した場合、メッセージの送信後に結果を記録する前にプロセスがクラッシュした場合。

## よくある問題 {#troubleshooting}

**チャネルを有効にして保存すると失敗し、「请求参数不符合要求，请检查后重试。」（リクエストのパラメーターが要件を満たしていません。確認してから再試行してください）と表示される**：フォームの入力に誤りがなければ、ほとんどの場合インスタンスの公開 URL が設定されていません。`app/config.yaml` に `notifications.instance_public_url` を設定してから、コンテナを作り直してください。

**保存時に「服务端暂时无法完成操作，数据没有被修改。」（サーバーは一時的に操作を完了できません。データは変更されていません）と表示される**：ほとんどの場合、暗号化マスターキーが設定されていません。`ecoku.env` に `ECOKU_NOTIFICATION_ENCRYPTION_KEY` を設定してから、コンテナを作り直してください。[Docker デプロイ](./docker#env)を参照してください。

**テストメールがタイムアウトする**：ほとんどの場合、サーバーの SMTP 送信ポートがブロックされています。まずサーバー上で `nc -vz smtp.example.com 465` を実行して接続できることを確認し、次にポートと暗号化方式が合っているか（465 は SSL/TLS、587 は STARTTLS）を確認してください。
