# v0.1.9

サービス停止とコールドバックアップ → 正確なイメージタグを変更 → `sudo docker compose pull && sudo docker compose up -d` → ヘルスチェックとロールバック準備。

このページは v0.1.9 リリース候補の説明です。まずコミットの CI 完了を待ち、その後タグとイメージ公開を確認してください。文書中のバージョン番号はイメージの公開済みを意味しません。

## v0.1.8 からの更新による影響

- SQLite は **schema v7** のままで、新しい移行はありません。データベース、コメント、設定、WAL、バックアップを削除・再作成しません。より古いバージョンからは既存の移行チェーンが適用されます。
- マウント、UID/GID `10001:10001`、ポート、ログ、環境変数、秘密情報は変更しません。本番設定とデータディレクトリを保持してください。
- 任意の `rate_limit.comment_list` は既定 **60**、期間は既存の `window_seconds`（既定 60 秒）です。このキーがない旧設定も起動できます。[設定リファレンス](../configuration)を参照してください。
- 上限内の成功レスポンスは既存 SDK と互換です。完全スレッドは **200 ノード、子孫 16 階層、1 MiB JSON** まで、集計プローブは同一サイト/ページの **10,000 件の ID/親関係**までです。超過時は切り詰めず **422** を返します。ルート `pageSize` を減らしても、単一の過大/過深スレッドや記事全体の集計超過は解消しません。現行 SDK は読み込み失敗を表示し、自動でモードを変更しません。
- 独自の組み込みは `parentId` / `afterId` で必要な単一階層だけを取得できます。[API リファレンス](../../reference/api)を参照してください。両モードは頻度制限、**同時 4 件**の枠、**2 秒の DB 読み取り期限**を共有します。混雑・期限切れは 503、頻度超過は 429 です。
- 制限は CORS の DB クエリより前に実行され、プリフライトや拒否された Origin も回数に含みます。早期拒否では未検証のクロスオリジン許可を追加せず、ブラウザーは読み込み失敗のみを表示する場合があります。`trusted_proxies` が正しくない場合、プロキシ経由の訪問者は同じ枠を共有します。[リバースプロキシ](../reverse-proxy)を確認し、全アドレスを信頼しないでください。
- SQLite 接続が再作成されても、外部キー、同期レベル、ビジータイムアウトを再適用します。トランザクションのキャンセルによる設定消失を防ぐ変更であり、schema 移行ではありません。

## 更新手順

1. CI/隔離環境で通常ページと大きなスレッドの動作を確認し、短い停止時間を確保します。無停止更新ではありません。
2. [バックアップと復元](../backup)に従い停止後にボリューム外のコールドバックアップを作成・確認します。`data/`、`app/config.yaml`、`ecoku.env`、旧 `compose.yaml` を保存し、稼働中の SQLite 主ファイルだけをコピーしないでください。
3. 公開済みイメージを確認して、本番 image だけを実際のレジストリの正確な `v0.1.9` タグに変更します。`registry.example.com/ecoku:v0.1.9` はプレースホルダーです。他の設定を上書きしないでください。
4. デプロイディレクトリで実行します：

   ```bash
   sudo docker compose config --quiet
   sudo docker compose pull && sudo docker compose up -d
   sudo docker compose ps
   sudo docker compose logs --tail=100 ecoku
   curl --fail --silent --show-error http://127.0.0.1:12123/api/health
   ```

5. ヘルス応答の `status: healthy` はプロセスが応答する証拠に限られます。コンテナーの健康状態、ログ、一覧、並べ替え、ページ切り替え、返信、管理画面も確認してください。本番で深いツリーや負荷テストを作成しないでください。

## v0.1.8 へのロールバック

まず停止します。`rate_limit.comment_list` を追加した場合は削除するか旧設定に戻してください。v0.1.8 は未知の YAML フィールドを拒否します。正確な `v0.1.8` タグに戻し、pull・起動後に動作を確認します。

v0.1.8 からの更新では両版が schema v7 のため、通常は現在の DB を保持してイメージだけ戻せます。バックアップ後の新規コメントも保持できます。データ異常が確認され、新規データの損失を受け入れる場合だけ、明示的にコールドバックアップ全体を復元してください。現在の DB を自動上書きしないでください。元の版が古い場合は対応する schema の復元条件に従います。ロールバックは CWE-400 を再導入するため、障害対応に限る措置です。

## CI と公開の順序

- `master` への push または `master` を対象とする PR で client/admin、VitePress ビルドと出力検証、Go テスト、vet、ビルドを実行します。
- テスト後、リリースコミットで `VERSION`、ルート `package.json`、Compose の正確なタグ、日付付き CHANGELOG v0.1.9 節とリンクを揃え、そのコミットの CI 成功も確認します。
- `v0.1.9` タグはバージョン整合性を検証し amd64/arm64 イメージと manifest を公開します。テスト再実行、本番デプロイ、本番 DB 操作は行いません。
- 文書サイトは別の `master` manual ワークフローで公開します。アプリのイメージタグでは公開されません。
