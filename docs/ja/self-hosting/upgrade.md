# アップグレード

現在のバージョンは **v0.2.8**（2026-10-01 リリース、schema v9）です。

## アップグレード時に起きること

アップグレードとは、`compose.yaml` のイメージを新しいバージョンに替えて起動することです。新しいバージョンは起動時にデータベースのスキーマバージョンを確認し、自分が対応するバージョンより低ければ、順番にマイグレーションを実行します。

- 各マイグレーションは 1 つのトランザクションで行われ、失敗するとその手順全体がロールバックされます。データベースは元のまま残り、サービスは起動しません。
- マイグレーションは元のデータベースファイル上で行われ、データベース、コメント、設定、WAL ファイル、バックアップを削除したり作り直したりすることはありません。
- 1 つの手順が終わるたびに、`schema_migrations` テーブルに記録が 1 行追加されます。
- **上方向へのマイグレーションしかできません**。旧バージョンのプログラムは、より新しいスキーマのデータベースを開けず、起動を拒否します。

そのため、アップグレード前のバックアップが、旧スキーマに戻す唯一の手段です。

複数のバージョンをまたいで直接アップグレードできます。たとえば v0.1.8 から v0.2.8 に直接替えると、途中のマイグレーションが順に実行されます。ただし、またいだ各バージョンのアップグレードノートはすべて読んでください。設定の変更が必要なバージョンもあります（たとえば [v0.2.4](./upgrades/v0.2.4) では `admin.token_ttl_minutes` を 480 にするか省略する必要があります）。

## 次のバージョンへの設定移行（未リリース） {#unreleased-config}

以下は未リリースの変更であり、v0.2.8 の再起動には適用しません。データベースは schema v9 のままで、既存のサイト、コメント、通知設定は残ります。ただし次の YAML フィールドを削除しないと、新しいバージョンは起動を拒否します。

| 削除する項目 | 新しい動作 |
| --- | --- |
| `site.port`、`site.log_path` | 12123 で待ち受け、ログを標準出力に書き込みます。ホスト側のポートは Compose で変更します。 |
| `client` と `database` セクション全体、および `admin.static_dir` | イメージ内のリソースとデータベースのパスは固定です。既存のデータマウントを維持します。 |
| `sites` セクション全体（`management_key_env` を含む） | 既存サイトは SQLite から読み取り、新しいサイトは管理画面で作成します。`EcokuSite` 認証は廃止します。 |
| `admin.enabled`、`admin.token_ttl_minutes`、`admin.username_env`、`admin.password_hash_env`、`admin.token_key_env`、`notifications.encryption_key_env` | 管理画面は常に有効で、セッションは 8 時間です。環境変数名は[設定リファレンス](../reference/configuration#env)を参照してください。 |

リリース後、次の順序で移行します。

1. [停止後のコールドバックアップ](./backup#cold-backup)でデータベース、元の設定、`ecoku.env`、Compose を保存し、検証します。実際の SQLite パスとホスト側のマウント先を記録してください。
2. 表の YAML フィールドと空になったセクションを削除します。`notifications.instance_public_url`、`site.trusted_proxies`、使用している `admin.allowed_origins` と `rate_limit` は残します。環境変数名を変えていた場合は標準名に戻し、**元のパスワードハッシュ、署名キー、暗号化マスターキーの値は維持**してください。
3. 既存のデータベースが `/data/ecoku.sqlite3` にマップされることを確認します。公式テンプレートならデータ移動は不要です。独自の保存場所では Compose のホスト側パスを調整します。独自のファイル名は停止中に `ecoku.sqlite3` にそろえ、`-wal` や `-shm` が残っていれば主ファイルと一緒にコピーして対応する名前に変え、元のコピーを残してください。主ファイルだけのコピーや空ディレクトリのマウントは避け、UID/GID `10001:10001` にディレクトリとファイルの読み書きを許可します。
4. Compose から `./app/logs:/var/log/ecoku` を削除します。古いログファイルは残せます。新しいログは `docker compose logs` で確認し、ローテーションは Docker で管理します。`EcokuSite` を使う自動化は有効な管理者セッションに変更するか、管理画面で操作してください。
5. その時点で公開された正確な tag に変更し、[アップグレード手順](#steps)に従って取得、起動、確認します。管理画面のサイト数、過去のコメント、通知設定が維持されていることを確認してください。

v0.2.8 に戻す場合はサービスを停止し、元の Compose、設定、環境変数を復元します。データベースを移動した場合は元のマウントが参照する場所に戻してください。schema は同じなのでデータベースの巻き戻しは不要です。古いバックアップで更新後のコメントを上書きしないでください。旧版のログディレクトリには引き続きコンテナユーザーの書き込み権限が必要です。

## アップグレード手順 {#steps}

**1. アップグレードノートを読む**。下の[バージョン一覧](#versions)で目的のバージョンを探し、設定の変更があるか、スキーマのマイグレーションを伴うかを確認します。

**2. 停止してコールドバックアップを取る。**[バックアップと復元](./backup#cold-backup)の手順を実行し、`Verified backup` と出力されることを確認します。

**3. イメージのバージョンを変更する。**`~/Ecoku/compose.yaml` を編集し、`image` を目的のバージョンに変えます。例：

```yaml
    image: "git.via.moe/dejavu/ecoku:v0.2.8"
```

正確なバージョン番号を書き、`latest` は使わないでください。アップグレードノートで `app/config.yaml` や `ecoku.env` の変更が求められている場合は、一緒に変更します。

**4. 取得して起動する。**

```bash
cd ~/Ecoku
sudo docker compose config --quiet
sudo docker compose pull
sudo docker compose up -d
```

**5. 確認する。**

```bash
sudo docker compose ps
sudo docker compose logs --tail=100 ecoku
curl --fail --silent --show-error http://127.0.0.1:12123/api/health
```

コンテナの状態が `healthy` になり、ログにエラーがないことを確認したら、ブログの記事ページと管理画面を開き、コメントの読み込みと投稿が正常にできること、管理画面にログインできることを確かめます。

## ロールバック

まず、新旧 2 つのバージョンのスキーマが同じかどうかを確認します（下表を参照）。

- **スキーマが同じ場合**：サービスを停止し、`compose.yaml` のイメージを旧バージョン番号に戻して、取得・起動します。データベースには手を付ける必要がなく、アップグレード後に投稿されたコメントも残ります。新しいバージョンの省略時のデフォルト値を使った場合は、先に旧バージョンが必要とする完全な設定を戻してください。新しいバージョンで設定項目を追加していて、旧バージョンがそれを認識しない場合は、先に削除してください。そうしないと、旧バージョンが未知のフィールドを理由に起動を拒否します。
- **スキーマが異なる場合**：イメージのバージョン番号を戻すだけでは足りません。旧バージョンはマイグレーション済みのデータベースを開けません。アップグレード前のコールドバックアップから[復元](./backup#restore)する必要があります。バックアップ後に投稿されたコメントや設定の変更は失われます。
