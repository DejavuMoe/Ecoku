# アップグレード

Compose の**正確なイメージ tag**だけを変更し、既存の Compose ファイル全体を上書きしないでください。手順は以下。各版の差分はページ末の索引を参照。

## 手順

1. 対象版の説明を読み、スキーマ・環境変数・マウントの変化を確認する。
2. [バックアップと復元](./backup) に従い停止コールドバックアップ（データベース、設定、秘密、Compose）。
3. 既存のリソース制限とマウントは残し、イメージ tag だけ変える。
4. 版の説明で環境変数や設定の追加が必要なら合わせて直す。
5. pull して起動し、ログとヘルスエンドポイントを確認する。
6. 管理ログイン、サイト、コメント、返信、通知、有効なボット対策を検証する。

```bash
sudo docker compose config --quiet
sudo docker compose pull
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail=200 ecoku
curl --fail http://127.0.0.1:12123/api/health
```

`/api/health` はプロセスが応答できることだけを示し、移行や依存がすべて正常であることまでは保証しません。

## データベース

移行は `data/ecoku.sqlite3` 内で版ごと・トランザクション単位で実行されます。成功時は `schema_migrations` レコードを追加するだけで、データベース・WAL・バックアップを自動削除しません。失敗した版は完了とマークされず、サービスは起動を拒否します。ダウングレード移行はありません。

| イメージ | Schema |
| --- | --- |
| `v0.1.0`–`v0.1.2` | v4 |
| `v0.1.3`–`v0.1.4` | v5 |
| `v0.1.5`–`v0.1.7` | v6 |
| `v0.1.8` | v7 |

より高いスキーマに書き込み済みのデータベースは、古いイメージにタグだけ戻しても動きません。停止前の全庫バックアップを復元してから、古い tag で起動してください。

## ロールバック

停止し、失敗現場を残し、[バックアップと復元](./backup) で復元し、Compose を古い正確な tag に戻してから起動します。
