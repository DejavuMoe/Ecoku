# アップグレード

公開バージョンは v0.3.0 以降です。新規環境は [Docker デプロイ](./docker) を参照してください。このページは既存環境の更新用です。

現在のバージョンは **v0.3.0**（2026-10-03 リリース、schema v11）です。

新しいイメージは GHCR に公開します。Forgejo のイメージを使う環境は、今後の更新で `image` を `ghcr.io/dejavumoe/ecoku:v0.3.0` または対象バージョンの固定 tag に変更し、既存のデータと設定のマウントを維持してください。Forgejo registry には新しいバージョンを公開しません。同じバージョンで取得元を切り替える際に、インスタンスの再初期化は不要です。

## アップグレード時に起きること

アップグレードとは、`compose.yaml` のイメージを新しいバージョンに替えて起動することです。新しいバージョンは起動時にデータベースのスキーマバージョンを確認し、自分が対応するバージョンより低ければ、順番にマイグレーションを実行します。

- 各マイグレーションは 1 つのトランザクションで行われ、失敗するとその手順全体がロールバックされます。データベースは元のまま残り、サービスは起動しません。
- マイグレーションは元のデータベースファイル上で行われ、データベース、コメント、設定、WAL ファイル、バックアップを削除したり作り直したりすることはありません。
- 1 つの手順が終わるたびに、`schema_migrations` テーブルに記録が 1 行追加されます。
- **上方向へのマイグレーションしかできません**。旧バージョンのプログラムは、より新しいスキーマのデータベースを開けず、起動を拒否します。

そのため、アップグレード前のバックアップが、旧スキーマに戻す唯一の手段です。

## アップグレード手順 {#steps}

**1. アップグレードノートを読む**。下の[バージョン一覧](#versions)で目的のバージョンを探し、設定の変更があるか、スキーマのマイグレーションを伴うかを確認します。

**2. 停止してコールドバックアップを取る。**[バックアップと復元](./backup#cold-backup)の手順を実行し、`Verified backup` と出力されることを確認します。

**3. イメージのバージョンを変更する。**`~/Ecoku/compose.yaml` を編集し、`image` を目的のバージョンに変えます。例：

```yaml
    image: "ghcr.io/dejavumoe/ecoku:v0.3.0"
```

正確なバージョン番号を書き、`latest` は使わないでください。アップグレードノートで `app/config.yaml` や `ecoku.env` の変更が求められている場合は、一緒に変更します。

**4. 取得して起動する。**

```bash
cd ~/Ecoku
sudo docker compose config --quiet
sudo docker compose pull
sudo docker compose up -d
```

**5. 確認する。**

```bash
sudo docker compose ps
sudo docker compose logs --tail=100 ecoku
curl --fail --silent --show-error http://127.0.0.1:12123/api/health
```

コンテナの状態が `healthy` になり、ログにエラーがないことを確認したら、ブログの記事ページと管理画面を開き、コメントの読み込みと投稿が正常にできること、管理画面にログインできることを確かめます。

## ロールバック

まず、新旧 2 つのバージョンのスキーマが同じかどうかを確認します（下表を参照）。

- **スキーマが同じ場合**：サービスを停止し、`compose.yaml` のイメージを旧バージョン番号に戻して、取得・起動します。データベースには手を付ける必要がなく、アップグレード後に投稿されたコメントも残ります。新しいバージョンの省略時のデフォルト値を使った場合は、先に旧バージョンが必要とする完全な設定を戻してください。新しいバージョンで設定項目を追加していて、旧バージョンがそれを認識しない場合は、先に削除してください。そうしないと、旧バージョンが未知のフィールドを理由に起動を拒否します。
- **スキーマが異なる場合**：イメージのバージョン番号を戻すだけでは足りません。旧バージョンはマイグレーション済みのデータベースを開けません。アップグレード前のコールドバックアップから[復元](./backup#restore)する必要があります。バックアップ後に投稿されたコメントや設定の変更は失われます。

<details id="legacy-config" class="details custom-block">
<summary>内部テスト環境の旧設定移行</summary>

v0.2.9 では schema v9 に v10 の管理者アカウントテーブルを追加します。既存のサイト、コメント、通知、CAPTCHA 設定、旧管理者認証情報は維持され、既存インスタンスは更新前に設定を変更する必要がありません。

以前の `compose.yaml`、`app/config.yaml`、`ecoku.env` を残し、[アップグレード手順](#steps)に従って停止バックアップ後に新しいイメージを起動します。初回起動で旧認証情報を移行し、通知暗号化キーを `data/ecoku-secrets.json` に保存します。旧ポート、ファイルログ、静的ディレクトリ、SQLite パス、YAML `sites`、`management_key_env` は互換動作を維持し、仮パスワードの生成や既存管理者へのパスワード変更要求は行いません。

動作を確認してから、次の手順で設定を簡略化します。

1. 管理画面にログインでき、サイト数、過去のコメント、通知設定が正しいことを確認します。
2. `data/ecoku-secrets.json` が作成され、認証情報の復号エラーがログにないことを確認します。
3. サービスを停止し、`data/` 全体、`app/config.yaml`、`compose.yaml`、古い `ecoku.env` をバックアップします。
4. 停止中に `ecoku.env` から管理者変数と `ECOKU_NOTIFICATION_ENCRYPTION_KEY` を削除します。必要な `TZ` は Compose の `environment` に移します。`ecoku.env` に残す場合は `env_file` も残してください。
5. 環境ファイルが不要になった場合だけ Compose から `env_file` を削除します。`TZ` やサイト管理キーを供給する場合は残してください。
6. `notifications.instance_public_url`、使用している `site.trusted_proxies`、`admin.allowed_origins`、`rate_limit` は残します。古いデータベースパス、ファイルログ、`EcokuSite` 自動化が不要なことを確認してから旧フィールドを削除します。
7. コンテナを作り直し、管理画面、コメント、通知を再確認します。

古い通知暗号化キーと `data/ecoku-secrets.json` が一致しない場合、既存の認証情報を壊さないため起動を拒否します。古いデータベースパスは有効なので、`database.sqlite.path` を削除して空の `/data` をマウントしないでください。

内部テスト版の本番ロールバック用イメージは提供しません。過去の schema の復元には当時の完全なコールドバックアップが必要です。ここでは設定移行の記録のみを残しています。

</details>
