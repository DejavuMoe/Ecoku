# アップグレード

現在のバージョンは **v0.2.6**（2026-09-29 リリース、schema v8）です。

## アップグレード時に起きること

アップグレードとは、`compose.yaml` のイメージを新しいバージョンに替えて起動することです。新しいバージョンは起動時にデータベースのスキーマバージョンを確認し、自分が対応するバージョンより低ければ、順番にマイグレーションを実行します。

- 各マイグレーションは 1 つのトランザクションで行われ、失敗するとその手順全体がロールバックされます。データベースは元のまま残り、サービスは起動しません。
- マイグレーションは元のデータベースファイル上で行われ、データベース、コメント、設定、WAL ファイル、バックアップを削除したり作り直したりすることはありません。
- 1 つの手順が終わるたびに、`schema_migrations` テーブルに記録が 1 行追加されます。
- **上方向へのマイグレーションしかできません**。旧バージョンのプログラムは、より新しいスキーマのデータベースを開けず、起動を拒否します。

そのため、アップグレード前のバックアップが、旧スキーマに戻す唯一の手段です。

複数のバージョンをまたいで直接アップグレードできます。たとえば v0.1.8 から v0.2.6 に直接替えると、途中のマイグレーションが順に実行されます。ただし、またいだ各バージョンのアップグレードノートはすべて読んでください。設定の変更が必要なバージョンもあります（たとえば [v0.2.4](./upgrades/v0.2.4) では `admin.token_ttl_minutes` を 480 にするか省略する必要があります）。

## アップグレード手順 {#steps}

**1. アップグレードノートを読む**。下の[バージョン一覧](#versions)で目的のバージョンを探し、設定の変更があるか、スキーマのマイグレーションを伴うかを確認します。

**2. 停止してコールドバックアップを取る。**[バックアップと復元](./backup#cold-backup)の手順を実行し、`Verified backup` と出力されることを確認します。

**3. イメージのバージョンを変更する。**`~/Ecoku/compose.yaml` を編集し、`image` を目的のバージョンに変えます。例：

```yaml
    image: "git.via.moe/dejavu/ecoku:v0.2.6"
```

正確なバージョン番号を書き、`latest` は使わないでください。アップグレードノートで `app/config.yaml` や `ecoku.env` の変更が求められている場合は、一緒に変更します。

**4. 取得して起動する。**

```bash
cd ~/Ecoku
sudo docker compose config --quiet
sudo docker compose pull
sudo docker compose up -d
```

**5. 確認する。**

```bash
sudo docker compose ps
sudo docker compose logs --tail=100 ecoku
curl --fail --silent --show-error http://127.0.0.1:12123/api/health
```

コンテナの状態が `healthy` になり、ログにエラーがないことを確認したら、ブログの記事ページと管理画面を開き、コメントの読み込みと投稿が正常にできること、管理画面にログインできることを確かめます。

## ロールバック

まず、新旧 2 つのバージョンのスキーマが同じかどうかを確認します（下表を参照）。

- **スキーマが同じ場合**：サービスを停止し、`compose.yaml` のイメージを旧バージョン番号に戻して、取得・起動します。データベースには手を付ける必要がなく、アップグレード後に投稿されたコメントも残ります。新しいバージョンで設定項目を追加していて、旧バージョンがそれを認識しない場合は、先に削除してください。そうしないと、旧バージョンが未知のフィールドを理由に起動を拒否します。
- **スキーマが異なる場合**：イメージのバージョン番号を戻すだけでは足りません。旧バージョンはマイグレーション済みのデータベースを開けません。アップグレード前のコールドバックアップから[復元](./backup#restore)する必要があります。バックアップ後に投稿されたコメントや設定の変更は失われます。
