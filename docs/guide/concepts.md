# 工作方式

本页说明 Ecoku 如何组织评论、如何处理删除和身份、保存了哪些数据。部署和接入前读一遍，可以避开大部分意外。

## 站点与页面 {#page-key}

Ecoku 用两个值确定「一篇文章的评论区」：

- **站点 ID**（`siteId`）：在后台注册站点时设定，一个实例可以有多个站点，彼此的评论、来源白名单和设置互不相通。
- **页面 key**（`pageKey`）：由接入代码提供，通常是文章的站内路径，如 `/posts/hello-world/`。

同一站点下，页面 key 相同的页面共享一个评论区。页面 key 必须是站内相对路径，最多 512 个字符，不能是完整 URL，也不能带 `?` 查询参数或 `#` 片段。带 `?`、`#` 或写成完整 URL 的 key 仍能显示评论区，但发表评论会被拒绝；超过 512 个字符时评论区无法初始化。

::: warning 页面 key 一旦使用就不要改
评论按页面 key 存储。如果之后调整了博客的永久链接格式，旧文章的页面 key 随之改变，原来的评论就不会再显示（数据仍在数据库中）。选页面 key 时，用一个不会变的值。
:::

## 讨论串与分页 {#threads}

评论是树状的：一条根评论下面可以有回复，回复下面还可以再回复。

- **层数**：根评论算第 0 层，新回复最多到第 16 层，所以第 16 层的评论不显示「回复」按钮。需要继续讨论时，请回复较上层的评论。
- **缩进**：缩进随层数增加，到第 3 层为止，更深的回复与第 3 层对齐。从第 3 层起，昵称行会显示可点击的 `@被回复者`，指向它回复的那条评论。这样深层讨论在手机上也不会被挤成窄条。
- **折叠**：有回复的评论旁边有 `[-]`，点击后折叠整个分支，显示「已折叠 N 条回复」。

分页只针对根评论。每页显示若干条根评论（默认 10 条），**连同它们下面的全部回复**一起返回。翻页时换的是一整批讨论，不会出现回复被拆到下一页的情况。

为了防止单个超大讨论拖垮服务，一次列表请求有上限：最多 200 条评论、16 层、1 MiB 的响应；统计总数时，同一页面最多检查 10,000 条评论。超过任何一项时，服务端返回错误而不是截断的数据，评论区显示加载失败。正常的博客评论很难触及这些上限；真的遇到时，可以调小每页根评论数，或在自定义前端里改用[逐层读取的接口](../reference/api#cursor)。

## 删除 {#deletion}

后台提供两种删除，都不可撤销：

**墓碑删除**：清空评论的昵称、邮箱、网址和正文，但保留它在讨论中的位置和时间。公开页面显示为「已删除」和「[该评论已删除]」，它下面的回复保持原样，不能再回复它。这样删掉一条评论不会让整串讨论失去上下文。

**彻底删除**：把一条墓碑从数据库中移除。只有下面**没有任何回复**的墓碑可以彻底删除。

## 访客身份 {#visitor-identity}

访客发评论不需要注册，只填三项：

| 字段 | 是否必填 | 是否公开 |
| --- | --- | --- |
| 昵称 | 必填，最多 80 个字符 | 公开 |
| 邮箱 | 默认必填，可在站点设置中改为选填 | 不公开，只用于回复通知 |
| 网址 | 默认选填，可改为必填；只接受 `http://` 或 `https://` | 公开，作为昵称上的链接 |

访客在根评论框填写的身份，回复时会自动带上。直接点某条评论下的「回复」时，缺少的身份信息就在这个回复框里填写，不会跳回页面顶部。

发布成功后，浏览器会记住这份身份 7 天，下次不必重填：

- 保存在浏览器的 IndexedDB 中，用一把不可导出的 AES-GCM 密钥加密，不写入 Cookie、localStorage 或 URL；
- 按 Ecoku 服务地址和站点 ID 分开保存，不同站点之间不共享；
- 7 天后失效；浏览器不支持、数据损坏或过期时，评论框回到空白状态，不影响发评论；
- 清除浏览器的站点数据即可删除它，评论区不另设「忘记我」按钮。

## 博主身份 {#blogger}

博主不需要单独的账号。在后台为站点设置博主昵称、邮箱和口令后，博主在评论区的**昵称栏**输入口令、邮箱和网址留空即可发布。服务端识别口令后：

- 把这条评论的昵称换成博主昵称，网址换成站点 URL，邮箱换成博主邮箱；
- 给这条评论打上博主标记，页面上在昵称后显示标志（默认 `[博主]`）；
- 浏览器清空昵称栏，也不把口令当作身份保存。

博主标记在评论保存时写入，之后不会重新计算。修改博主昵称、更换口令都不会改变已有评论的标记。

只有两个场景会根据「昵称与博主昵称一致、邮箱与博主邮箱一致（不区分大小写）」回填历史评论的博主标记：从旧版本升级到 schema v5 时的一次性迁移，以及 [Twikoo 首次导入](../self-hosting/twikoo)。

## 纯文本

评论正文、昵称永远按纯文本显示：

- HTML 标签原样显示为文字，不会被解析；
- 不渲染 Markdown，不把网址自动变成链接；
- 换行保留。

唯一的例外是 [Smoji 表情](../integration/smoji)：站点启用表情包后，符合格式与站点图片来源规则的 `![smoji:名称](图片地址)` 会显示为图片，其余一律按文字显示。默认使用清单来源，管理员也可以另行指定图片来源，见[清单与图片分别托管](../integration/smoji#hosting)。

访客网址只作为昵称上的链接出现，带有 `rel="nofollow ugc noopener noreferrer"`。

## 保存和公开的数据 {#data}

每条评论在数据库中保存：站点 ID、页面 key、文章标题、父评论、昵称、邮箱、网址、正文、博主标记、删除时间、创建和更新时间。

公开接口返回的只有：评论 ID、站点 ID、页面 key、父评论 ID、昵称、网址、正文、是否博主、是否已删除和时间。**邮箱不会出现在任何公开接口中。**

Ecoku 不保存访客的 IP、User-Agent 或地理位置，日志里也不记录这些信息。IP 只在内存中短暂用于限流，进程重启后清空。评论区不请求任何第三方头像、统计或 IP 查询服务。

以下情况会让访客浏览器直接连接第三方：

- 启用了 Turnstile 或 Cap 时，加载验证组件；
- 启用了 Smoji 时，浏览器从清单和图片各自所在的服务器加载资源。

## 来源校验与限流

每个站点在后台登记「允许来源」。浏览器读取评论时，不在名单中的来源会被拒绝；提交评论时，请求必须带有已登记的来源，否则直接拒绝。所以评论区只能在你登记过的网站上使用。

提交、读取、删除和后台登录都按 IP 限流，默认每分钟 5 次提交、60 次读取。放在反向代理后面时，需要正确配置 [`trusted_proxies`](../self-hosting/reverse-proxy#trusted-proxies)，否则所有访客会共用一个额度。

## 时间与时区

评论时间以 `YYYY-MM-DD HH:mm` 显示，时区由 Compose `environment` 中的 `TZ` 决定，部署模板中为 `Asia/Shanghai`，见 [时区与后台语言](../self-hosting/docker#timezone)。悬停在时间上可查看时区和偏移。
