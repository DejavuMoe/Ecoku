# v0.1.9

Stop and take a cold backup → change the exact image tag → `sudo docker compose pull && sudo docker compose up -d` → health checks and rollback readiness.

These are the upgrade notes for v0.1.9, dated 2026-08-31. Before deploying, confirm that the image publishing pipeline for the tag has succeeded. A version mentioned in documentation does not establish that its image is available.

## Impact when upgrading from v0.1.8

- SQLite remains at **schema v7** with no new migration. No database, comments, settings, WAL or backups are deleted or recreated. Older versions still follow the existing migration chain.
- Mounts, UID/GID `10001:10001`, ports, logging, environment variables and secrets are unchanged. Keep the production configuration and data directory.
- Optional `rate_limit.comment_list` defaults to **60** per existing `window_seconds` window (default 60 seconds). Old configurations still start without adding this key. See [Configuration](../configuration).
- Successful responses remain compatible with the existing SDK. Complete-thread reads are limited to **200 nodes, 16 descendant levels and 1 MiB JSON**, with a count-probe budget of **10,000 ID/parent records per site/page**. Exceeding a budget returns **422**, not a partial tree. A smaller root `pageSize` cannot solve a single oversized/deep thread or an article exceeding the count budget. The current SDK shows a load failure and does not switch modes.
- Custom integrations can read one level on demand with `parentId` / `afterId`; see [API reference](../../reference/api). Both modes share read rate limits, **4 concurrent slots** and a **2-second database-read deadline**. Saturation or timeout returns 503; rate limiting returns 429.
- Admission runs before CORS database queries, counting preflights and rejected origins too. Early rejection does not add unverified cross-origin permissions; browsers may only show a load failure. Visitors behind a proxy may share its quota unless `trusted_proxies` is configured correctly. Review [Reverse proxy](../reverse-proxy); never trust all addresses.
- Every new or replacement SQLite connection reapplies foreign-key, synchronous and busy-timeout settings, including after canceled transactions. This is not a schema migration.

## Upgrade

1. Validate normal pages and large-thread behavior in CI/an isolated environment, then schedule a short outage. This procedure is not zero-downtime.
2. Follow [Backup and restore](../backup): stop the service and create/verify an off-volume cold backup of `data/`, `app/config.yaml`, `ecoku.env` and the original `compose.yaml`. Do not copy only the main SQLite file while the service is running.
3. After the image is published, change only the production image to the exact `v0.1.9` tag in your registry. `registry.example.com/ecoku:v0.1.9` is a placeholder. Preserve other production settings.
4. Run in the deployment directory:

   ```bash
   sudo docker compose config --quiet
   sudo docker compose pull && sudo docker compose up -d
   sudo docker compose ps
   sudo docker compose logs --tail=100 ecoku
   curl --fail --silent --show-error http://127.0.0.1:12123/api/health
   ```

5. The health endpoint returns `status: healthy`, which only proves process responsiveness. Also check container health/logs and the site's listing, sorting, pagination, replies and admin interface. Do not generate deep trees or load-test production.

## Roll back to v0.1.8

Stop the service first. Remove an explicitly added `rate_limit.comment_list` key or restore the previous configuration: v0.1.8 rejects unknown YAML fields. Restore the exact `v0.1.8` image tag, pull/start and recheck health and behavior.

Both versions use schema v7, so an upgrade from v0.1.8 normally permits an image rollback without restoring the database, preserving new comments. Restore the full cold backup only for confirmed data problems and with acceptance that post-backup data will be lost. Do not automatically overwrite the current database. For an older starting version, follow its schema rollback rules. Rolling back reintroduces CWE-400 and should only be an incident fallback.

## CI and release order

- A `master` push or PR targeting `master` runs client/admin checks, VitePress build/output checks, Go tests, vet and build.
- The release commit aligns `VERSION`, root `package.json`, the exact Compose image and the dated CHANGELOG v0.1.9 section/links. Commit CI and tag image publishing are independent workflows.
- The `v0.1.9` tag only checks version consistency and builds/publishes amd64/arm64 images and the manifest. It does not rerun tests, deploy production or access production databases.
- The docs site is published separately through a `master` manual workflow, not by the application image tag.
