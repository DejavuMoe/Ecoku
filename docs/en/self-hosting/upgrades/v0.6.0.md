# v0.6.0

- Release date: 2026-11-17
- Schema: v12 (no migration)
- Image: `ghcr.io/dejavumoe/ecoku:v0.6.0`
- npm SDK: `ecoku@0.6.0`

## Changes {#changes}

- The final runtime image migrated to distroless Debian 13 static pinned by multi-arch digest (`gcr.io/distroless/static-debian13:nonroot`), continuing to run as numeric UID/GID `10001:10001` (instead of distroless default 65532). The server binary and static assets are owned by root, and `/data` is owned by the runtime user; the build stage still uses Alpine.
- The runtime image no longer contains a shell (`/bin/sh`), `wget`, or package managers (`apk`, `apt`), reducing attack surface.
- Added a built-in `healthcheck [--port=12123]` CLI probe that requests only loopback `http://127.0.0.1:<port>/api/health` with a 2-second timeout, without reading configuration, opening the SQLite database, or initializing secrets. The port range is 1..65535, exiting silently with code 0 on success.
- CI and release verification add runtime checks on both architectures, including non-root execution, a read-only root filesystem and the absence of a shell. Automated tests use v0.5.7 pinned by digest to verify upgrades, new comment writes and data preservation after rollback.

## Compatibility {#compatibility}

- There is no database migration; schema remains v12. Existing data directories with correct `10001:10001` permissions need no adjustment; the image does not change mounted directory ownership or permissions at startup. Keep existing data and read-only configuration mounts, configuration options and persistent secrets, including custom data paths.
- **Healthcheck probe change (breaking configuration change)**: Because the new image does not contain `wget`, any older Compose file that overrides the healthcheck with a `wget` command must be updated to `test: ["CMD", "/app/ecoku-server", "healthcheck"]`. If a custom container port is configured, specify `--port` explicitly on the probe.
- Official images use OCI media types (multi-arch manifest index), requiring Docker / container runtime support for standard OCI images; the host operating system does not need Debian 13.
- Logs still use stdout / stderr by default; existing file logging configuration remains effective. Troubleshoot from the host using `docker compose logs`, `docker inspect`, and `docker cp`. The image has no shell; invoke the server binary directly (e.g. `docker compose exec ecoku /app/ecoku-server <subcommand>`).
- The browser SDK is published as `0.6.0` to align with the server release; its API and behavior remain identical to 0.5.7 without new APIs or behavior changes.
- When upgrading across multiple releases from older versions, check earlier compatibility notes (such as [v0.5.4 compatibility](./v0.5.4#compatibility), [v0.5.2 first sign-in](./v0.5.2#compatibility), and [v0.5.0 origin conflicts](./v0.5.0#compatibility)).

## Upgrade {#upgrade}

Follow the [upgrade steps](../upgrade#steps) to stop the service and make a cold backup. Change the image to `ghcr.io/dejavumoe/ecoku:v0.6.0`, update the Compose healthcheck to `test: ["CMD", "/app/ecoku-server", "healthcheck"]` (appending `--port` if using a custom port), then pull the image, recreate the container, and wait for health.

Confirm that the container status becomes `healthy`, and verify admin login, existing and new comments, and any configured notifications and CAPTCHA. Sites integrating independently through npm may update to `ecoku@0.6.0` as desired.

## Rollback {#rollback}

Stop the service, change the image back to v0.5.7 and restore its `wget` probe in Compose, then pull and recreate the container. Alternatively, remove the Compose `healthcheck` override to use the old image's built-in probe. The old image does not support the `healthcheck` subcommand.

The schema remains v12, so rolling back to v0.5.7 does not require database restoration, and comments and data added during v0.6.0 are preserved. For rollbacks across different schemas, follow [backup restoration](../backup#restore).
