# v0.6.0

- 发布日期：2026-11-17
- schema：v12（无迁移）
- 镜像：`ghcr.io/dejavumoe/ecoku:v0.6.0`
- npm SDK：`ecoku@0.6.0`

## 变更 {#changes}

- 最终运行镜像迁移至固定多架构 digest 的 distroless Debian 13 static（`gcr.io/distroless/static-debian13:nonroot`），继续使用 UID/GID `10001:10001`（非 distroless 默认的 65532），程序二进制与前端静态资源归 root 所有，数据目录 `/data` 归运行用户所有；构建阶段仍使用 Alpine。
- 运行镜像不再包含 shell（`/bin/sh`）、`wget` 或包管理器（`apk`、`apt`），进一步收敛攻击面。
- 新增镜像内置的 `healthcheck [--port=12123]` 命令行探针，只请求回环地址 `http://127.0.0.1:<port>/api/health`，2 秒超时，不读取配置文件、不打开数据库、不初始化密钥，端口范围为 1～65535，成功静默退出（exit 0）。
- CI 与发布流程增加双架构镜像的无 shell、非 root、只读根文件系统等运行时检查，并使用固定 digest 的 v0.5.7 作为基线运行自动化升级、写入新评论与回滚数据校验。

## 兼容性 {#compatibility}

- 没有新增数据库迁移，schema 保持 v12 不变。已有 `10001:10001` 正确权限的数据目录无需调整；镜像启动时不会修改挂载目录的属主或权限。保留现有的数据与只读配置挂载、配置参数及持久密钥，包括自定义数据路径。
- **健康检查探针变更（破坏性配置变动）**：因新镜像不包含 `wget`，旧 Compose 中若配置了基于 `wget` 的健康检查覆盖，升级后必须替换为 `test: ["CMD", "/app/ecoku-server", "healthcheck"]`。若自定义了容器服务端口，须同步在探针中显式指定 `--port`。
- 官方镜像使用 OCI media types（多架构 manifest index），要求宿主 Docker / 容器运行时能拉取 OCI 镜像，无需宿主升级到 Debian 13。
- 默认日志继续输出至 stdout / stderr，已有文件日志配置仍生效。排障在宿主使用 `docker compose logs`、`docker inspect`、`docker cp`。镜像不含 shell，运维直接执行二进制命令（如 `docker compose exec ecoku /app/ecoku-server <子命令>`）。
- 浏览器 SDK 仅对齐发布版本号为 `0.6.0`，接口与对外行为延续 0.5.7，无新的 API 或行为变更。
- 跨版本从更早版本升级时，仍须依次查阅前序版本的兼容性说明（如 [v0.5.4 的兼容性说明](./v0.5.4#compatibility)、[v0.5.2 的首次登录说明](./v0.5.2#compatibility)、[v0.5.0 的来源冲突与历史数据说明](./v0.5.0#compatibility)）。

## 升级 {#upgrade}

按 [升级步骤](../upgrade#steps) 停服并冷备份，将镜像改为 `ghcr.io/dejavumoe/ecoku:v0.6.0`，并将 Compose 的健康检查改为 `test: ["CMD", "/app/ecoku-server", "healthcheck"]`（自定义端口时追加 `--port`），再拉取镜像、重建容器并等待健康。

检查服务容器状态为 `healthy`，验证管理后台登录、已有评论读取、新评论提交，以及已配置的通知与人机验证。独立使用 npm SDK 的网站可按需更新至 `ecoku@0.6.0`。

## 回滚 {#rollback}

先停止服务，将镜像改回 v0.5.7，并恢复旧 Compose 的 `wget` 探针，再拉取并重建容器。也可以删除 Compose 中的 `healthcheck` 覆盖，使用旧镜像自带探针。旧镜像不支持 `healthcheck` 子命令。

schema 保持 v12，回滚至 v0.5.7 无需恢复数据库，升级后新增的评论和数据会正常保留。跨 schema 回滚仍须按 [备份恢复](../backup#restore) 操作。
