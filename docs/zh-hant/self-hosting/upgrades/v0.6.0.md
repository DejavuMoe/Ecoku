# v0.6.0

- 發布日期：2026-11-17
- schema：v12（無遷移）
- 映像檔：`ghcr.io/dejavumoe/ecoku:v0.6.0`
- npm SDK：`ecoku@0.6.0`

## 變更 {#changes}

- 最終執行映像檔遷移至固定多架構 digest 的 distroless Debian 13 static（`gcr.io/distroless/static-debian13:nonroot`），繼續使用 UID/GID `10001:10001`（非 distroless 預設的 65532），程式二進位檔案與前端靜態資源歸 root 所有，資料目錄 `/data` 歸執行使用者所有；建置階段仍使用 Alpine。
- 執行映像檔不再包含 shell（`/bin/sh`）、`wget` 或套件管理器（`apk`、`apt`），進一步收斂受攻擊面。
- 新增映像檔內建的 `healthcheck [--port=12123]` 命令列探針，只請求回環位址 `http://127.0.0.1:<port>/api/health`，2 秒逾時，不讀取設定檔、不開啟資料庫、不初始化金鑰，連接埠範圍為 1～65535，成功靜默結束（exit 0）。
- CI 與發布流程增加雙架構映像檔的無 shell、非 root、唯讀根檔案系統等執行時檢查，並使用固定 digest 的 v0.5.7 作為基準執行自動化升級、寫入新評論與回滾資料校驗。

## 相容性 {#compatibility}

- 沒有新增資料庫遷移，schema 保持 v12 不變。已有 `10001:10001` 正確權限的資料目錄無需調整；映像檔啟動時不會修改掛載目錄的擁有者或權限。保留現有的資料與唯讀設定掛載、設定參數及持久金鑰，包括自訂資料路徑。
- **健康檢查探針變更（破壞性設定變更）**：因新映像檔不包含 `wget`，舊 Compose 中若設定了基於 `wget` 的健康檢查覆蓋，升級後必須替換為 `test: ["CMD", "/app/ecoku-server", "healthcheck"]`。若自訂了容器服務連接埠，須同步在探針中顯式指定 `--port`。
- 官方映像檔使用 OCI media types（多架構 manifest index），要求主機 Docker / 容器執行時能拉取 OCI 映像檔，無需主機升級至 Debian 13。
- 預設日誌繼續輸出至 stdout / stderr，既有檔案日誌設定仍生效。排障在主機使用 `docker compose logs`、`docker inspect`、`docker cp`。映像檔不含 shell，維運直接執行二進位命令（如 `docker compose exec ecoku /app/ecoku-server <子命令>`）。
- 瀏覽器 SDK 僅對齊發布版本號為 `0.6.0`，介面與對外行為延續 0.5.7，無新的 API 或行為變更。
- 跨版本從更早版本升級時，仍須依序查閱前序版本的相容性說明（如 [v0.5.4 的相容性說明](./v0.5.4#compatibility)、[v0.5.2 的首次登入說明](./v0.5.2#compatibility)、[v0.5.0 的來源衝突與歷史資料說明](./v0.5.0#compatibility)）。

## 升級 {#upgrade}

依 [升級步驟](../upgrade#steps) 停服並冷備份，將映像檔改為 `ghcr.io/dejavumoe/ecoku:v0.6.0`，並將 Compose 的健康檢查改為 `test: ["CMD", "/app/ecoku-server", "healthcheck"]`（自訂連接埠時追加 `--port`），再拉取映像檔、重建容器並等待健康。

檢查服務容器狀態為 `healthy`，驗證管理後台登入、既有評論讀取、新評論提交，以及已設定的通知與人機驗證。獨立使用 npm SDK 的網站可依需求更新至 `ecoku@0.6.0`。

## 回滾 {#rollback}

先停止服務，將映像檔改回 v0.5.7，並恢復舊 Compose 的 `wget` 探針，再拉取並重建容器。也可以刪除 Compose 中的 `healthcheck` 覆蓋，使用舊映像檔自帶探針。舊映像檔不支援 `healthcheck` 子命令。

schema 保持 v12，回滾至 v0.5.7 無需還原資料庫，升級後新增的評論和資料會正常保留。跨 schema 回滾仍須依 [備份還原](../backup#restore) 操作。
