# Toolchain and dependency decisions

Start with the versions actually resolved in the lockfile, CI image, published artifact and deployment. Compare each candidate with an in-place fix and the supported version of the incumbent. Distinguish end of support, a security advisory, removal from a distribution, a preview feature and a newer release. Each has a different consequence. Record which applies, its official source and date, the support window required by this project, and the migration work. An advisory needs the installed version, affected configuration and available fix. [OSV data sources](https://osv.dev/docs/) and [Go vulnerability management](https://go.dev/doc/security/vuln/)

The tool documentation linked here was consulted on 2026-11-18. Check the release available on the target when applying it.

## Choosing a version manager

Use mise when developers and CI have demonstrable version drift, or when the project already declares it. Map which file owns each pin. Use the project's existing manager and dependency lockfile, and its frozen or locked installation mode in CI. A mise tool lock can pin tool binaries separately. On a version of mise that supports the project's `packageManager` declaration, let that declaration supply the manager version. Otherwise pin the executable once and verify its resolved version in both environments. Preserve offline bootstrap, checksums, workspaces and publish behavior the project relies on. [mise tool selection](https://mise.jdx.dev/dev-tools/) and [mise Node.js package-manager support](https://mise.jdx.dev/lang/node.html)

Node.js stopped bundling Corepack in v25. Standalone Corepack is a viable choice for workflows that use its semantics. Consult the declared manager's installation guide and the project's supported Node versions before choosing between standalone Corepack, mise or the manager's direct installer. A change in tool distribution alone has no bearing on application dependencies. [Corepack distribution](https://github.com/nodejs/corepack#readme), [Yarn's guidance](https://yarnpkg.com/corepack) and [pnpm installation](https://pnpm.io/installation)

## JavaScript, TypeScript and web delivery

| Decision | Check on the actual project |
| --- | --- |
| ESLint to Oxlint, Prettier or Biome formatting to Oxfmt | Map enabled rules, type-aware checks, plugins, framework files, ignores and editor hooks. Run old and new on the same files and known violations. Keep a narrow existing check for uncovered rules. Verify formatting is idempotent and review the diff size. Biome's lint and import organization are separate responsibilities. [Oxlint migration](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint) and [Oxfmt migration](https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier) |
| dotenv to `node --env-file` | Exercise each real launch path, missing files, quoting, multiple files, precedence over or under process variables, expansion and programmatic loading used by this app. Inspect child processes and build/test runners. Use synthetic values. [Node environment files](https://nodejs.org/api/environment_variables.html) |
| tsx or Bun scripts to native Node TypeScript | Try the oldest supported Node on a real script. Check erasable syntax, module resolution, explicit extensions, aliases, JSX/TSX and workspace packages. Native stripping ignores tsconfig transformations. Keep a separate type gate and verify the published entry point. [Node TypeScript support](https://nodejs.org/api/typescript.html) |
| `tsc` to `bun check` | Inspect the pinned Bun and its help, TS version, project references, editor and framework diagnostics, declaration emit and package resolution. A package script named `check` shadows the built-in on versions documented by Bun. Use `bun check --no-script` only when that version supports it. Keep declaration generation and Svelte diagnostics when used. Compare a good project and intentionally wrong code in a disposable fixture. [Bun's differences from tsc](https://bun.com/docs/runtime/check) and [Svelte diagnostics](https://svelte.dev/docs/cli/sv-check) |
| Zod, Valibot or ArkType | Identify boundary inputs and consumers. Compare coercion, defaults, transforms, async refinements, error paths, schema export and bundle cost on the project's schemas. Standard Schema lets consumers accept multiple libraries. Use shared test inputs to establish parsing parity. [Standard Schema specification](https://standardschema.dev/) |
| Current bundler, Vite/SvelteKit, tsdown or Node SEA | Match the artifact to its consumer. Test a static site on an ordinary HTTP server, SSR with a self-hosted adapter, a library as an installed tarball (exports and declarations), or a single-executable CLI on each target OS/architecture with its assets and native add-ons. Use tsdown as a library candidate, SEA when single-file distribution pays for its packaging cost. Keep a working build if the promised outcome is already met. [Vite migration](https://vite.dev/guide/migration), [SvelteKit Node adapter](https://svelte.dev/docs/kit/adapter-node), [tsdown](https://tsdown.dev/guide/) and [Node SEA](https://nodejs.org/api/single-executable-applications.html) |

## Other ecosystems

| Project signal | Candidate and acceptance evidence |
| --- | --- |
| Go service or CLI with high CPU, heap growth or contention | Check the supported Go line, module/toolchain directives, build tags and CGO/cross-build constraints. Profile with pprof or tracing. Compare realistic benchmarks and concurrency tests on a supported target. Try SQL, allocation or synchronization fixes before changing language. [Go diagnostics](https://go.dev/doc/diagnostics) and [release policy](https://go.dev/doc/devel/release) |
| Rust component with slow builds, large binaries or a costly hot path | Check the declared minimum supported Rust version, Cargo features, duplicates, native dependencies and target triples. Measure release builds under the same feature set. Verify downstream consumers with the minimum compiler and supported feature combinations before trimming. [Cargo features](https://doc.rust-lang.org/cargo/reference/features.html) and [minimum Rust version](https://doc.rust-lang.org/cargo/reference/rust-version.html) |
| Python service, package or data job | Compare interpreter support and wheel/platform availability. Evaluate uv for reproducible installs, Ruff for the checks it actually covers, or a native extension only for a measured CPU hotspot. Exercise clean locked installs, tests and a built wheel in a consumer environment. Give mise or uv clear ownership of interpreter selection if both are present. [Python support](https://devguide.python.org/versions/), [uv project sync](https://docs.astral.sh/uv/concepts/projects/sync/) and [Ruff rules](https://docs.astral.sh/ruff/linter/) |
| Another runtime or framework | Use its support policy, runtime profile and distribution contract. For example, a .NET CLI evaluating Native AOT must test reflection, trimming, native libraries and target-specific publish output. Apply the same comparison to an explicitly requested Go, Rust, Python or TypeScript target. [Native AOT limitations](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/) |

End with the candidates that could change a decision. For each, say what to keep, change, trial or defer, the local evidence for that judgment and what would overturn it.
