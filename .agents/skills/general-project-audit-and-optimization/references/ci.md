# CI, test selection and trusted results

Trace one representative PR through queue time, setup, critical-path jobs, retries and the last required result. Compare typical and tail wall time, runner-minutes, memory and flaky failures. Separate queue time from execution and cold from warm caches. For a small, fast suite, a full run can cost less than maintaining a selector or distributing setup. Set a target with a floor for coverage and a ceiling for resource use.

## Evaluate four independent changes

| Change | Implementation decision | Acceptance evidence |
| --- | --- | --- |
| Balance shards by duration | Use stable test or file IDs and recent successful timings for comparable platforms. Sort runnable units longest first. Assign each to the currently lightest shard. Estimate unseen units from comparable tests and update after each run. Keep serial fixtures together and isolate per-shard state. | Across shards the union equals the intended suite with no accidental overlap. Compare slowest shard, total wall time and runner-minutes, including setup. For 75, 45, 24 and 6 seconds, two independent shards can each carry 75 seconds before setup. [Timing-based splitting](https://circleci.com/docs/guides/optimize/parallelism-faster-jobs/) and [Playwright sharding](https://playwright.dev/docs/test-sharding) |
| Select tests affected by a PR | Use `git diff --name-status -M <merge-base> <head>` with verified revisions. Include changed tests, both names of renames, deleted paths from the base graph and transitive **dependents** in the import or project graph. Include non-imported inputs such as fixtures, templates, schemas, generated code, dynamic plugins, workspace configuration and lockfiles. Prefer an existing project-aware selector. | Run the selected list alongside full runs on representative PRs before enforcing it. Check historical failures and report tests missed. Unknown base, incomplete history/graph, unmodelled global changes or an unexplained empty selection trigger the full suite on that PR. Retain full runs on integration/release or a scheduled cadence, with a response to discrepancies. [Nx affected analysis](https://nx.dev/docs/features/ci-features/affected) and [Vitest affected tests](https://vitest.dev/guide/recipes/affected-tests) |
| Replace slow lint or type checks | Inventory the old command's duties, including type-aware or framework checks, declaration emit, editor integration and lint plugins. Compare the candidate on the same project and known-good/known-bad fixtures. Check the pinned binary and any script named `check`. Keep a residual check where the faster tool lacks coverage. | Detect the intended failures, build the same artifacts and measure the complete job, including setup. Preserve a downstream consumer test for public packages. [Toolchain decision guide](toolchains.md) |
| Parallelize independent jobs | Model real dependencies between lint, type check, build and tests. Run independent work together. Preserve generated code, build artifacts and shared-service ordering where required. Bound workers by cores, RAM, service capacity and runner budget. Key reusable artifacts and caches to relevant inputs and platform. | Compare time to first actionable failure, time to all required results, runner-minutes and memory. Check that cancellation, missing artifacts or a failed prerequisite cannot produce a successful gate. |

## Keep the meaning of a green check

- Run required checks on the actual revision being merged, including merge-group events when a queue is used. Record base, head, tested SHA, run/attempt, intended suite, commands and conclusions. Examine code-scanning **results** at the required severity and coverage. A completed scanner job establishes execution only. Treat an intentional empty selection separately from failed discovery. Account for path-filtered workflows and skipped or cancelled prerequisites in the final gate. [GitHub required check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) and [code scanning merge protection](https://docs.github.com/en/enterprise-cloud%40latest/code-security/concepts/code-scanning/merge-protection)
- Keep untrusted PR builds isolated from credentials, privileged runners and release jobs. Keep control of required checks and approval with a trusted source, particularly when a diff changes the checks themselves. A benign known-failing fixture can establish that a required gate rejects the change. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use)
- Match verification to the failure. An architecture boundary, type or existing linter rule can prevent a recurring error cheaply. A contract test or state invariant can catch runtime failures. Add deterministic or property-based cases for important transitions. Use formal modelling only for a critical property whose assumptions can be stated and tested against the implementation. Judge success by defects caught, feedback time and recovery.

## When self-hosted agent automation is requested

Start from a working local check and a human-reviewed change. A self-hosted Forgejo runner can run existing CI. A local mini-SWE-agent can handle a bounded coding task, OpenHands offers a broader local agent environment, and PR-Agent is a candidate for review-only feedback. Verify each component's license, maintenance, model endpoint, data egress, credentials and host support on the decision date. Running a frontend or runner locally can still leave the model or control plane hosted elsewhere. Choose the smallest piece that fills the identified gap. Keep automated merging and deployment subject to the owner's existing authorization and independent gates. [Forgejo Actions](https://forgejo.org/docs/latest/admin/actions/), [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent), [OpenHands](https://github.com/OpenHands/OpenHands) and [PR-Agent](https://github.com/The-PR-Agent/pr-agent)
