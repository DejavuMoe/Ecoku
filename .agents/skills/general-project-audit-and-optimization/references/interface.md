# Interface, state and accessibility review

Start from the people using the interface, their task and a failure that costs them time, data or confidence. For an app-wide state review, inventory each distinct flow and its owner. Inspect navigation, form flags, requests, cached data, server state, optimistic updates, timers and persisted drafts for implicit transitions. Group repeated uses of the same component. Report which screens or flows you could not inspect.

For each consequential transition record **current state, event, guard, next state, effect, recovery**. Trace success as well as empty, loading, partial, error, retry, cancellation, offline, revoked access and stale responses where reachable. Specify an invariant a test can observe. For example, after search B completes, a late response from search A must leave B's results on screen. An accessible status announcement and keyboard focus also belong to the result when users depend on them.

Judge a change along three axes. **UX** covers task completion, avoidable decisions and recovery. **DX** covers a clear owner of state, a comprehensible transition and a regression test. **AX** (agent experience) covers a discoverable entry point, stable accessible names and a deterministic way to exercise and observe the flow. State the trade-off when one dimension regresses. Prefer an existing state owner, derived state or a small reducer. Introduce a statechart or library only if it meaningfully simplifies real transitions. A diagram earns its place when it exposes an ambiguity that a short transition table misses.

## Apply the requested visual defaults

| Area | Design decision and check |
| --- | --- |
| Copy and hierarchy | Remove the middle dot `·` when used as a UI copy separator. Preserve punctuation in proper names and user data. Use vocabulary familiar to the intended audience, a length appropriate to the control, and consistent action verbs. Remove explanatory filler, invented terms and decorative or repeated eyebrows/overlines. Keep labels, errors, instructions and recovery information the task requires. Use spacing and font weight to establish hierarchy. |
| Choices | Put a decision where the user intends to make it. Give common, reversible actions a sensible default. Preserve confirmation or undo for consequential actions. Order information by what the user needs to do next. |
| Color | Map all application-controlled UI colors to semantic tokens backed by Radix Colors, including hover, selected, error, text, borders and overlays. Use steps 1–2 for surfaces, 3–5 for component backgrounds, 6–8 for edges, 9–10 for solid fills, 11–12 for text. Check each actual foreground/background pair in light and dark modes. Some high-chroma fills need dark text. Identify platform forced colors, external assets or user-authored colors separately. Reuse the palette through the project's existing styling system. [Radix scale roles](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale) |
| Alignment and shape | Check baselines, icon optical centers and aligned edges. For concentric nested corners start with inner radius equal to outer radius minus inset, floored at zero, then inspect the rendered result. Favor spacing over unneeded boxes. Use radii and shadows when they communicate grouping or elevation. Remove decorative colored stripes on card edges. |
| Lines and type | Use 0.5 CSS px for a needed hairline where it remains visible at the target pixel density and zoom. Keep focus indicators, control boundaries and hit areas perceptible. Favor three text sizes per screen, four at most under the requested design default. Use 12 CSS px as the floor for secondary web text, choose comfortable body text, and allow text scaling. Use native scalable units on other platforms. |
| Motion | Minimize transitions. When motion explains a change, start with ease-out around 250 ms, adjust to the interaction and honor reduced-motion settings. Keyboard users and automated tests must be able to proceed when the actual state is ready. [W3C reduced motion technique](https://www.w3.org/WAI/WCAG22/Techniques/css/C39) |

## Accept the result

Run a representative flow at target widths, with keyboard only, visible focus, accessible names and announced status. Check a failure and its recovery, light/dark themes when supported, zoom or text resizing to 200%, and reduced motion. Combine a screenshot for layout with assertions for behavior. Check the actual target or note what emulator/browser was used. For web content, WCAG 2.2 AA normally requires 4.5:1 for ordinary text and 3:1 for large text. Relevant non-text control information needs 3:1 against adjacent colors. Check target size or the applicable spacing exception. When a visual default harms access, preserve access and record the specific exception. [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) and [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
